# Audit technique — RadarPulse
**Date :** 7 mars 2026
**Périmètre :** `apps/web` (React/TypeScript) · `supabase/functions` (Edge Functions Deno) · `supabase/migrations` (PostgreSQL)

---

## Résumé exécutif

Le projet est bien structuré pour un early-stage SaaS. L'architecture feature-first côté frontend, l'injection de dépendances dans les Edge Functions, et la cohérence des migrations sont des points positifs solides. Les problèmes identifiés se concentrent autour de la gestion de session, d'un module mort, et de quelques risques de sécurité DB à corriger.

**Priorité haute (à corriger avant la mise en production) :** 3 items
**Priorité moyenne (impact UX ou maintenabilité) :** 4 items
**Priorité basse (code smell / amélioration) :** 5 items

---

## 🔴 Priorité haute

### 1. Session non persistée — utilisateurs déconnectés à chaque rechargement

**Fichier :** `apps/web/src/lib/supabase.ts`

```ts
// Actuel
export const supabase = createClient(ENV.SUPABASE_URL, ENV.SUPABASE_ANON_KEY, {
  auth: { persistSession: false, autoRefreshToken: false, detectSessionInUrl: false },
});
```

`persistSession: false` + `autoRefreshToken: false` signifie qu'aucun token n'est stocké entre les rechargements de page. Chaque refresh renvoie l'utilisateur vers la landing page. De plus, `useAuthUser` appelle `getUser()` une seule fois au montage — si le token expire en cours de session, l'UI ne réagit pas.

**Correction :**
```ts
export const supabase = createClient(ENV.SUPABASE_URL, ENV.SUPABASE_ANON_KEY, {
  auth: {
    persistSession: true,
    autoRefreshToken: true,
    detectSessionInUrl: true,
  },
});
```

Et dans `useAuthUser`, abonner aux changements d'état :
```ts
useEffect(() => {
  const { data: { subscription } } = supabase.auth.onAuthStateChange((_event, session) => {
    setUser(session?.user ?? null);
    setLoading(false);
  });
  return () => subscription.unsubscribe();
}, []);
```

### 2. Vues PostgreSQL accessibles à `anon` sans RLS côté données

**Fichier :** migrations `20260301091000`, `20260301090000`, etc.

Les vues `opportunities_search_v1` et `opportunities_inbox_it_v1` ont un `grant select to anon`. Si quelqu'un accède à ces vues directement via l'API REST PostgREST (sans passer par l'Edge Function), il peut lire toutes les opportunités sans authentification ni vérification d'abonnement.

**Correction :** Révoquer l'accès `anon` sur ces vues et laisser uniquement `authenticated` + `service_role`. L'Edge Function utilise `service_role` via `sbAdmin()`, donc cela ne casse rien.

```sql
revoke select on public.opportunities_search_v1 from anon;
revoke select on public.opportunities_inbox_it_v1 from anon;
```

### 3. Variables d'environnement non validées au démarrage

**Fichier :** `apps/web/src/lib/env.ts`

```ts
export const ENV = {
  SUPABASE_URL: import.meta.env.VITE_SUPABASE_URL as string,
  SUPABASE_ANON_KEY: import.meta.env.VITE_SUPABASE_ANON_KEY as string,
  ...
```

Le cast `as string` masque le fait que ces valeurs peuvent être `undefined`. Si `.env` est absent ou incomplet, l'app compile sans erreur mais crashe silencieusement à l'exécution (fetch vers `undefined/functions/v1/...`).

**Correction :**
```ts
function requireEnv(key: string): string {
  const v = import.meta.env[key];
  if (!v) throw new Error(`Missing required env var: ${key}`);
  return v as string;
}

export const ENV = {
  SUPABASE_URL: requireEnv("VITE_SUPABASE_URL"),
  SUPABASE_ANON_KEY: requireEnv("VITE_SUPABASE_ANON_KEY"),
  ...
};
```

## 🟡 Priorité moyenne

### 4. SettingsPage en double — fichier mort

**Fichiers :** `apps/web/src/App.tsx` (ligne ~115) et `apps/web/src/features/settings/SettingsPage.tsx`

`App.tsx` définit une `function SettingsPage()` inline. Le fichier `features/settings/SettingsPage.tsx` existe mais n'est jamais importé — il est mort. Tout changement fait dans l'un ne se reflète pas dans l'autre.

**Correction :** Supprimer la définition inline dans `App.tsx` et importer depuis `@/features/settings/SettingsPage`.

---

### 5. `InboxAccessGate` — vérification d'abonnement non réactive

**Fichier :** `apps/web/src/App.tsx`

Le check d'abonnement (`subscriptions` query) n'est déclenché qu'au montage du composant. Si l'abonnement expire pendant une session active (ex. : onglet ouvert toute la journée), l'utilisateur garde accès à l'Inbox sans nouvelle vérification.

**Correction :** Ajouter un interval de re-vérification toutes les 15 minutes, ou valider côté Edge Function à chaque requête (ce que `opportunities-search` fait déjà partiellement — il suffit de le rendre strict sur le 402).

---

### 6. CORS trop ouvert sur les Edge Functions

**Fichier :** `supabase/functions/_shared/cors.ts`

```ts
"Access-Control-Allow-Origin": "*",
```

Toutes les Edge Functions acceptent des requêtes depuis n'importe quelle origine. En production, cela devrait être restreint au domaine de l'app.

**Correction :**
```ts
const ALLOWED_ORIGIN = Deno.env.get("ALLOWED_ORIGIN") ?? "https://radarpulse.io";
export const corsHeaders = {
  "Access-Control-Allow-Origin": ALLOWED_ORIGIN,
  ...
};
```

---

### 7. `sbAdmin()` crée un nouveau client à chaque appel dans `worker`

**Fichier :** `supabase/functions/worker/index.ts`

Le singleton `_sb` est correct dans `worker`, mais `sbAdmin()` dans `_shared/db.ts` crée un nouveau client à chaque appel (pas de cache). Dans des fonctions à fort volume comme `worker` ou `dispatcher`, cela génère des connexions superflues.

**Correction :** Mettre en place un module-level singleton dans `_shared/db.ts` :
```ts
let _client: ReturnType<typeof createClient> | null = null;
export function sbAdmin() {
  if (_client) return _client;
  // ... init ...
  _client = createClient(url, serviceKey, { ... });
  return _client;
}
```

## 🔵 Priorité basse (code quality)

### 8. Utilisation excessive de `any` dans les types

**Fichiers :** `lib/types.ts` (`meta: any`, `raw: any`, `payload: any`), `App.tsx` (`(user.app_metadata as any)`).

Ces `any` contournent la sécurité TypeScript. Ils devraient être typés avec `Record<string, unknown>` au minimum, ou avec des types dédiés.

---

### 9. Filtre `minQuality` — UX ambiguë

**Fichier :** `apps/web/src/features/inbox/InboxPage.tsx`

Le placeholder dit `"es. 0.7"` et le label `"Qualita minima (0-1)"`. Un utilisateur non technique pourrait entrer `70` pensant à un pourcentage. Comme le code fait `Math.max(0, Math.min(1, parsed))`, `70` serait silencieusement converti en `1`, filtrant presque tous les résultats sans explication.

**Correction :** Afficher un message de validation si la valeur dépasse 1 : `"Entrez une valeur entre 0 et 1 (ex. 0.7 = 70%)"`.

---

### 10. Pas de fichier `.env.example`

Le projet utilise plusieurs variables d'environnement (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_STRIPE_PLAN_PRICE`, `VITE_STRIPE_PLAN_NAME`, `VITE_SHOW_DEV_APP`) mais aucun `.env.example` n'est fourni. Un nouveau développeur devra lire le code pour les découvrir.

---

### 11. Pas de boundary d'erreur React

**Fichier :** `apps/web/src/main.tsx` (et `App.tsx`)

Il n'y a aucun `<ErrorBoundary>` autour des routes. Une exception non catchée dans n'importe quel composant affichera un écran blanc sans message d'erreur.

---

### 12. `originType` absent des filtres UI

**Fichier :** `apps/web/src/features/inbox/InboxPage.tsx`

Le hook `useInboxData` accepte `originType` dans ses filtres, et l'Edge Function `opportunities-search` supporte `origin_type`. Mais aucun contrôle UI n'expose ce filtre à l'utilisateur alors que la donnée est affichée sur chaque carte. C'est une feature manquante.

---

## Points positifs notables

- **Race condition bien gérée** dans `useInboxData` via `requestVersionRef` — évite les mises à jour d'état orphelines sur des requêtes abandonnées.
- **Injection de dépendances** dans `opportunities-search/index.ts` (`OpportunitiesSearchDeps`) — permet de tester la logique métier sans Supabase réel.
- **Validation défensive** dans `edgeFunctions.ts` (`asItem`, `asCursor`) — le frontend ne plante pas si l'Edge Function renvoie une shape inattendue.
- **Migration ordonnée et traçable** — les noms de fichiers sont préfixés avec des timestamps et décrivent précisément leur contenu.
- **RLS bien appliqué** sur `access_requests` — insert anonyme autorisé, lecture réservée au `service_role`.
- **Trigger PostgreSQL** `trg_compute_opportunity_quality` — calcul automatique et cohérent des scores qualité côté DB.
